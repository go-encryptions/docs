# argon2 — Argon2 with a NEON kernel

`github.com/go-encryptions/argon2` (v0.1.2)

```go
import "github.com/go-encryptions/argon2"

key := argon2.IDKey(password, salt, 3, 64*1024, 4, 32)
```

Argon2 ([RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html)): the API and the
code of `golang.org/x/crypto/argon2`, plus an Advanced SIMD (NEON) kernel for the
BLAMKA compression function on arm64, where the standard package runs scalar Go.
`Key` and `IDKey` are the same functions with the same results; only the speed
differs. One difference in failure: `keyLen == 0` panics with
`argon2: key length too small`, where `x/crypto/argon2` (v0.59.0) crashes with a
nil-pointer dereference. As in `x/crypto`, `time == 0` and `threads == 0` also
panic. Written from the [README](https://github.com/go-encryptions/argon2).

| Platform | BLAMKA |
|---|---|
| arm64 with Armv8.2 SHA-3 (every Apple core, Neoverse V1 and later) | NEON, `XAR` for each XOR-and-rotate |
| arm64 | NEON |
| amd64 | SSE4.1 (unchanged from x/crypto) |
| loong64 | LSX (unchanged from x/crypto) |
| anything else | portable Go |

The arm64 kernels are generated by `tools/genblamka`, and CI checks that the
committed assembly is the generator's output.

**Correctness.** The x/crypto test vectors, a differential test of every kernel
against the portable code on random blocks (including `out` aliasing an input),
and a test of `Key` and `IDKey` against `golang.org/x/crypto/argon2` over several
parameter sets.

**Measured, and where.** From the README at tag v0.1.1. Argon2id, t=3, m=64 MiB,
one lane, 32-byte output, one core, Go 1.27.4. The reference is libsodium 1.0.22
`crypto_pwhash`, compared by [refbench](https://github.com/go-scikit/refbench)
with the harness of go-theca/theca (theca v0.7.0, argon2 v0.1.0): interleaved
rounds, every round under a 1-minute load of 8, output compared byte for byte.

| Machine | This package | libsodium 1.0.22 | Ratio | `x/crypto/argon2` |
|---|---:|---:|---:|---:|
| Apple M4 Max | 48.9 ms | 66.5 ms | 0.73 | 93.6 ms |
| AMD Ryzen 9 7950X (Zen 4), pinned to one core | 66.4 ms | 262 ms | 0.25 | 66.4 ms (same code) |

On arm64 the NEON kernel is 1.9 times faster than x/crypto and 1.36 times faster
than libsodium. On amd64 this package is x/crypto's SSE4.1 code unchanged, so no
speed-up over x/crypto is claimed there. libsodium's 262 ms on Zen 4 is
libsodium's own: a C program calling `crypto_pwhash` on the same core takes 265 ms
with two different builds of 1.0.22, both reporting AVX2 and AVX-512F.

Used by [theca](https://go-theca.github.io/docs/) v0.7.0 (0.73 of libsodium on
the M4 Max).
